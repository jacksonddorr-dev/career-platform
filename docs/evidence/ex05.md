# ex05

## 1. Setting and prediction

I am using the given simulation. This was the command that failed: curl -Iv https://site.lab.example/ as well as the dig command. I expected dig to return the CNAME of current-app.up.railway.app. I expected the CURL command to connect to Railway and verify the certificate as well as returning HTTP 200 with the same page the Railway URL serves.


## 2. Failed check and evidence
The given simulated output: 
$ dig site.lab.example A +noall +answer
site.lab.example.  300  IN  A  198.51.100.24

$ curl -Iv https://site.lab.example/
* Connected to site.lab.example (198.51.100.24) port 443
* Server certificate: subject: CN=old-vm.lab.example
* SSL: certificate subject name does not match target host name 'site.lab.example'
curl: (60) SSL certificate problem: certificate subject name does not match target host name

The actual result: dig still returns the old A record (198.51.100.24) instead of the Railway CNAME, so curl connected to that IP on port 443. Then the HTTPS check failed with the curl error 60 since the certificate subject name of "old-vm.lab.example" doesn't match the current target host name.


## 3. Diagnosis

The DNS destination is site.lab.example which resolves to the old IP of the Azure A record rather than the Railway CNAME. The server at this IP presented an older TLS certificate rather than the current one, which resulted in the curl error 60.


## 4. Repair and repeated check

I did not run this output only interpret: 
$ dig site.lab.example A +noall +answer
site.lab.example.  300  IN  CNAME  current-app.up.railway.app.
current-app.up.railway.app.  300  IN  A  203.0.113.44

$ curl -Iv https://site.lab.example/
* Connected to site.lab.example (203.0.113.44) port 443
* Server certificate: subject: CN=site.lab.example
* SSL certificate verify ok.
< HTTP/2 200
The old command pointing to the IP in the old Azure A record has been replaced by the CNAME to Railway's target. This now reroutes to 203.0.113.44 IP. This change also fixed the curl error since the target is found and the HTTP goes through with a 200 response.


## 5. What you learned

I learned how to review and check for certain errors. I also learned that TLS errors aren't always a TLS problem considering this DNS problem caused both a DNS and TLS error.
