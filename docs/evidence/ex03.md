## 3. What went wrong, how I investigated, and what confirmed the fix

### 3.1 No lock file for `uv sync --locked`

- **What happened:** The plan said "uv sync from the lock file", but the repo had no `uv.lock`, and `uv` wasn't installed on the laptop.
- **How it was found:** `git ls-files` listed no `uv.lock`.
- **What confirmed the fix:** After running `uv lock` on the laptop and committing and pushing only `uv.lock`, `uv lock --check` exited 0, the 11 tests passed, and on the VM `uv sync --locked` installed 28 packages.

**In my own words:**
The migration plan assumed the VM would install packages from a lock file, but the repo didn't have one and uv wasn't installed.
&nbsp; 
uv.lock records the exact version so the lock had to be created on the laptop and pushed before the VM could use it 
&nbsp;
I generated and pushed the lock as well as the passing check and tests for a clean install on the VM server to run the version that was tested
&nbsp;

### 3.2 Running the tests overwrote my snapshot file

- **What happened:** `pytest` rewrote `data/public-profile.json` with a fake test profile, because the tests don't use a separate snapshot path.
- **How it was found:** The file's uncommitted diff disappeared from `git status`, and its modified time matched the moment the tests ran.
- **What confirmed the fix:** Running `uv run python -m app.snapshot` rebuilt the file from the real DB, and the diff was back to exactly 90 insertions and 9 deletions. The DB itself was untouched (its modified time was still Sep 22).

### 3.3 The admin password didn't save, and nano left a copy of my secrets

- **What happened:** My nano edit to `.env` never saved. nano stayed open, and when it closed it left `.env.save`, which held a different password and wasn't gitignored.
- **How it was found:** `grep -c replace- .env` still returned 1, the file's modified time hadn't changed, and `pgrep -a nano` showed nano still running.
- **What confirmed the fix:** I set the password with a hidden-prompt command instead. After that, `grep -c replace- .env` returned 0. `.env.save` was deleted, and `git status` on the VM was clean.

### 3.4 The PID file pointed at the wrong process, and SSH hung

- **What happened:** Starting uvicorn with `cd … && nohup … &` sent the whole chain to the background, so the PID file saved a wrapper bash (3304) instead of uvicorn (3306), and the SSH session never returned.
- **How it was found:** `ps` on the saved PID showed `bash -c …`, while `ss -ltnp` showed uvicorn under a different PID.
- **What confirmed the fix:** Putting `cd` on its own line and adding `< /dev/null` fixed it. The PID in the file now matches uvicorn's PID in `ss`, and SSH returns immediately.

**In my own words:**

&nbsp;

&nbsp;

### 3.5 The check for a running app gave false alarms

- **What happened:** `pgrep -f "uvicorn app.main"` reported the app as running when it wasn't, because it matched the text of its own SSH command.
- **How it was found:** The matching process was the `bash -c` running the check itself.
- **What confirmed the fix:** Switching to `pgrep -x uvicorn` and checking port 8000 with `ss -ltnH "sport = :8000"` both returned 0 before start and 1 after.

### 3.6 SSH stopped working after the VM was stopped and the network changed

- **What happened:** The next day the VM was `deallocated` and uvicorn wasn't running. When it came back, SSH timed out because my laptop's IP had changed and the NSG rule still allowed only the old one.
- **How it was found:** `az vm get-instance-view` showed the power state, and comparing my current IP with the `Allow-SSH-Laptop` rule's source showed the mismatch.
- **What confirmed the fix:** After updating the rule's source to my current IP, `ssh` connected again. I then restarted uvicorn, and health returned 200.
